状态：2026-10-05，实施与定向验收完成，0.6.0 条件交付。见 [第六轮报告](reports/round-6.md)。下文调查与方案保留为历史依据，调查时“未实施/未联网”不代表当前交付状态；前五轮未重新审查，个人数据未恢复。

## 证据与成因分级

用户两张截图分别显示：发送 ping 失败且存在两条重复错误；设置中 Provider 已保存，但模型均未验证，对话模型未选择；checkbox 与文案分行、居中，列表按钮挤压内容。

### F6-01 / 高：保存连接并不等于可以发送，配置失败原因被吞掉

源码确认：`packages/gui/src/main/provider-settings.ts` 的 acquireTurnProviders（约517–553行）先解析会话/全局绑定，缺失时抛“请先为黑塔和执行器选择 Provider 与模型”；执行模型必须 tools-available、revision 匹配且 tools supported，否则拒绝。`RoundThreeWorkbench.tsx` submit（约211–258行）仅对 needsKey 特判，其他异常统一写成“检查 Provider 配置或网络”；发送前未做有效绑定/验证状态预检。

截图中的全局未绑定、模型未验证可触发这一条本地失败链路。这是高置信解释，但没有读取当时会话覆盖或错误日志，不能把该次请求根因最终断言为缺绑定，更不能断言 Key/网络/Base URL 出错。用户的 root 与此前兼容服务实测形式一致，不应盲目要求加 /v1 或切协议。

修复方案：

- 提供主进程权威 readiness 结果：有效绑定、凭据状态、能力验证及 revision；返回稳定错误码和脱敏说明，不向 renderer 暴露密钥。
- 保存 Provider 后进入明确“选择模型→验证→设为当前默认→完成”流程，可一键引导完成；未经用户动作不自动请求服务或静默产生费用。默认同一模型供黑塔/执行器，分开选择放高级设置。
- 发送前检测实际会话的有效配置；不可用时保留草稿，显示具体原因和“完成配置/验证模型”按钮，不先启动失败轮次。服务端仍复查，防止配置变更竞态，不能只靠禁用按钮。
- 区分本地未绑定、验证过期、无密钥、鉴权失败、模型不存在、限流、超时/断流、协议不兼容；单一主错误组件，折叠脱敏技术详情，禁止直接展示带凭据的原始异常。
- 失败不同时显示“就绪”和两份错误；配置修好后的重试必须是用户动作，禁止重放既有工具。

待复核：若完成有效绑定和同 revision 工具验证后仍失败，记录协议/模型/端点路径、HTTP 状态、失败阶段和 request ID（若有），再定位传输层。用户本地配置即可，不在文档中抄 API Key；没有必要提前索取密钥。

### F6-02 / 中：checkbox 与通用输入框样式冲突

`ProviderSettings.tsx` 约717行：裸 label 包含 checkbox 和文本，无专用布局。`round-three.css` 约85行 `.herta-r3 input` 对所有 input 设 width:100%、padding:8px；设置挂在该工作台中，极可能与截图 checkbox 被放大占行一致。本次未获取运行时 computedStyle，因此记为源码支持的高置信布局成因，实施时确认样式命中。

修复：文本/密码输入选择器排除 checkbox/radio；增加 provider-checkbox-row 的 inline-flex/flex、align-items:center、gap:8px；checkbox width/height 固定16–18px、padding:0、flex-shrink:0。点击文案可切换、Tab/Space 正常。同时检查其他 HTTP 同意复选框，禁止为当前截图用绝对定位补丁。

### F6-03 / 中：不同布局容器造成错位与重复信息

round-two.css composer max-width:868px；round-three.css transcript max-width:880px；外层错误位于不同容器，消息内还有本轮错误，截图中左右起点不一致。设置列表用横向 flex，与长 URL/模型说明及两个按钮争夺空间。默认托管工作区用目录 basename 展示，截图将 UUID 当项目名称，是显示回退问题。

修复：统一内容宽度/左右padding令牌（建议最大880px，24px间距），消息、错误卡、审批和composer共用同一内容列；设置主内容使用 minmax(0,1fr)、操作列固定或窄屏下移。托管目录显示“临时工作区”并在详情保留真实路径。统一设置导航行高/按钮尺寸，避免大量重边框。检查100/150/200%和窄窗口，不仅看不溢出，还核对控件对齐。

## 2026-10-04 用户新增需求与范围决定

本节补充并覆盖前文“仅修配置和样式”的范围。用户测试继续，按下面阶段交付，保留原 R6-01 至 R6-05。

### R6-06 权限档位：本轮必需

源码已有 ApprovalPolicy/workspace-trust 和 get/setWorkspaceTrust；trusted仅覆盖部分工作区动作，网络/工作区外/破坏性类不在其内，不能把开关改名就称完全访问。

在输入区附近提供显眼且持久的模式选择，三档为产品提案：

| 档位 | 行为 |
| --- | --- |
| 只读/讨论 | 不修改文件，不运行有副作用命令；需要写入时提示切档，不能由模型自行放开 |
| 工作区编辑（默认） | 自动允许已定义的项目内常规读写/命令；网络、越界和其他需确认行为按明确规则审批，展示确切范围 |
| 完全访问 | 用户明确选择后，允许当前OS用户权限下项目内外文件和命令/网络操作，取消逐项工具审批；不自动提权，不绕过OS权限，不承诺OS沙箱，不把现有路径限制仍拒绝的行为包装成已开放 |

完全访问切换时一次清晰展示其范围，确认后不反复批准同范围操作；切换由用户触发，模型/项目文件/提示注入不能改档。所有执行入口在主进程使用统一策略，权限范围与审批频率不能只有UI改了。必须审查现有硬拒绝/路径边界，明确哪些为用户选择可放开的工具政策，哪些是输入校验、IPC来源、凭据隔离等不应随档位删除的应用完整性保护。

项目默认档位、会话覆盖、活动轮次快照保持可追溯；升级权限不自动重放待审工具，需要显式继续。降档对后续派发立即生效，不声称能撤回已执行副作用；已运行命令提供停止。后台旧会话不能因为当前UI改档无声提升权限。

验收用临时项目及第二个隔离目录：同一写入/命令在三档效果准确；完全访问可操作隔离的工作区外测试文件且不弹每步审批；拒绝伪造档位请求，持久化/重启行为明确。不要用真实个人目录做开放权限测试。

### R6-07 项目与任务管理：本轮必需

现有 deleteSession IPC可复用但先核查实际语义；新工作台缺项目实体/置顶管理的完整证据，不以“最近目录”冒充项目层级。

- 侧栏按项目分组，任务归属稳定projectId；展开/收起项目，项目内新建任务；无目录任务归临时工作区分组。
- 项目及任务支持置顶/取消置顶、重命名和删除/移除菜单；置顶顺序稳定，任务置顶在所属项目内，避免双处复制导致混淆。
- “移除项目”默认仅移除导航关联，不删除磁盘代码；若要同时删除任务记录，明确独立选择与数量提示。任务删除仅删除应用记录/附件，绝不回滚项目代码。
- 优先可撤销移除或回收区，最终清除再明确确认。运行中任务不能直接删除：先停止/取消等待项，再由用户完成删除；失败保留可恢复记录。
- 项目根改名/路径别名/同名不同目录、历史孤立任务、已有会话配置继承都要迁移兼容；不重建全部历史。

验收：两个项目同名不同路径、各含任务；新建/置顶/重启/删除/撤销后关系与绑定正确，磁盘源码不变。项目模式与任务权限继承一致。
