## 一、目标与优先级

The Herta 是带有大黑塔个性、可实际使用的 Windows 桌面编程助手。核心闭环仍是：配置模型 → 提出任务 → 受控执行 → 补充决定 → 阅读过程和真实文件改动。聊天是同级独立入口，不因增加记忆而获得项目读写或命令权限。简约、清晰、可靠优先；保留深紫角色风格，新增白/灰白浅色模式，不改成网页产品或装饰性演示。

按以下顺序推进，可分阶段验收，不能用插件开发拖延故障修复：

| 顺序 | 交付 | 必须达到 |
| --- | --- | --- |
| A / P0 | 执行失败定位、添加与验证合并 | 已验证模型的运行时异常有准确原因；未验证模型不能被激活 |
| B / P1 | 按协议支持的联网搜索 | 开关真正控制请求、搜索过程及来源可见 |
| C / P1 | 聊天记忆最小闭环 | 空闲整理、召回、用户保存/更正/删除，可检查且不会复活已忘记内容 |
| D / P1 | 回收区退场、文案和双主题 | 工作台更简洁，浅色与深色全流程可读 |
| E / 可选后续 | 插件接口设计与最小原型 | 基于扩展接口添加能力，不让插件直接改写应用自身 |

候选版本号在实际打包前决定，不预先承诺所有功能一次发布。A 应先独立通过，再合入 B/C/D；E 不作为本轮完成门槛。

## 二、已查到的事实：截图中的失败

截图显示先有 7 条成功工具操作，然后出现 `protocol-incompatible · stream`。它说明后续请求失败，不能说明前面操作未发生，也不能证明模型未验证。图中“未记录到可确认的文件变更”与成功写文件卡并存，文件快照归属/采集也需要核查。

当前代码：

- `packages/gui/src/main/provider-settings.ts` 已校验当前 Provider revision、协议、文本验证状态；执行器还要求 tools-available 和 tools supported。需要检查全部入口是否一致，而不是再次添加一个仅前端生效的门槛。
- `packages/providers/src/protocols/schema.ts::validatedCall` 将缺失标识、超限参数、未声明工具、JSON 不完整、schema 不匹配等归为 tool-args。
- `packages/gui/src/shared/provider-failure.ts` 将 tool-args 统一映射为“请验证模型工具能力”。这个建议对运行中偶发坏参数不够准确。
- 协议适配器负责 SSE 参数拼接、结束原因与 ready 事件；必须检查 length/截断、流式片段、同批多工具、结束事件重复及 schema 方言。

**尚未确定截图此次请求的具体坏参数或失败工具。** 本次只做源码静态排查，不能将某一猜测写成已确认根因。下一阶段只读提取该失败轮已保存的最小诊断；若原记录不足，先补诊断再在隔离目录小规模复现，不能把用户真实网站任务自动重跑。

### A1：诊断与恢复

1. 保存固定分类：参数截断 / 非法 JSON / schema 不符 / 未知工具 / 超限 / 流身份或结束异常。附工具名、调用 ID、finish reason、参数长度、schema 失败路径和类型；不默认保存完整参数、正文或凭据。
2. 区分模型验证状态与本次调用合法性。验证通过不保证每一次生成都合法；瞬时坏参数不自动清除历史验证状态。
3. 检查完整工具链：声明 schema → wire 编码 → 流拼接 → 参数验证 → 执行器。若是适配器丢字段，修适配器；若是合法截断，显示预算问题；不使用任意 JSON 修补后直接执行。
4. 保留成功调用与磁盘结果；“该调用未执行”必须指向具体失败调用。同一调用 ID 不重复执行。首版保留显式继续，不自动重新发送整轮；后续如需模型修正参数，必须以已有成功结果续接且限制次数。
5. 对照实际磁盘、快照和轮次记录，修复“成功写入但无变更列表”若确有采集缺陷。无法确认归属时保留准确说明，不为了美观编造 diff。

验收：已验证模型先成功写入、再返回坏调用；前者保留一次，后者不执行，提示具体原因。覆盖参数截断、schema 错误与并行调用边界，正常协议路径不退化。

### A2：添加的最后一步即验证

流程：选择预设/自定义 → Key 与模型 → 选择用途（聊天 / 编程，默认按当前入口）→ **保存并验证** → 显示结果并完成绑定。

- 聊天验证文本；编程验证文本与工具往返，测试工具由隔离的无副作用探针执行，不能读写用户项目。验证代表有限能力探测，不声称验证了所有业务工具。
- 新增多个模型只验证当前选中项；其他保留“未验证”不可用，不批量消耗余额。获取模型列表仍不等于验证。
- 失败保持输入和已加密保存的连接草稿，可修正后重试；不启用、不覆盖原可用绑定。允许取消或仅保存草稿，但不能因此绕过可用性门槛。
- revision/Key/协议/端点改变使相关验证失效；验证过程中再次编辑、取消、切页时丢弃过时结果。元数据修改是否使验证失效按已有规则复核，避免无谓重测。
- 首次成功时在同一流程提供“用于聊天/设为工作台默认”的直接选项；不要悄悄替换用户已有两种角色绑定。
- 检查 composer、纯聊天、角色/执行器绑定、IPC 与后台入口；界面禁用未验证项，主进程也拒绝。已有通过验证的配置无需强制重配。

## 三、联网搜索

权限控件右侧增加「联网搜索」开关；聊天输入区也提供相同入口。默认关闭，按会话保存；本轮开始时冻结选项，切换模型后重新核对能力。标签“允许搜索”不暗示每轮一定搜索。

这是**服务端搜索能力**开关，不是系统防火墙，也不禁止 API 本身联网。工作台命令访问网络仍受原权限机制约束，帮助提示说明这一界限即可，不能宣称关闭搜索等于完全离线。

能力应按端点身份、协议、模型和工具版本判定，不按 Provider 显示名称猜测。定义 supported / unsupported / unknown；未接入或未知禁用并说明，禁止通用地给每家发一个 web_search 字段。

调研结果与首批路径：

- [OpenAI Responses 搜索](https://developers.openai.com/api/docs/guides/tools-web-search)：专用服务器工具、过程事件和引用需要单独解析，不能当作本地函数调用执行。
- [Anthropic 搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)：按官方支持型号及工具版本实现，处理搜索结果块、引用和单轮调用上限。
- [Gemini Search Grounding](https://ai.google.dev/gemini-api/docs/google-search/) 与 [兼容接口](https://ai.google.dev/gemini-api/docs/openai)：先验证当前兼容路线的确切字段和来源元数据；若需要原生协议适配，作为独立模块，不假设标准 Chat Completions 已覆盖。
- DeepSeek 需要区分协议：[Responses 文档](https://api-docs.deepseek.com/guides/responses_api/)列出内置搜索工具被忽略；[Anthropic / Claude Code 接入说明](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/)明确介绍搜索能力。因此优先调查 Anthropic 路径的确切协议并以授权 Key 小量验证；不能给现有 Chat/Responses 连接虚假开启，也不自动替换用户连接协议。
- Qwen/Kimi/GLM 在实际接入前逐项查官方文档；支持名单是经过适配的组合，不是所有预设一并点亮。

定义独立 search-request/search-result/citation 事件。展示查询和来源链接、失败状态；只对实际返回来源标注引用。关掉时请求不携带搜索工具，开了但服务拒绝时明确报告，不冒充已搜索。结果是外部资料，不作为应用指令。限制单轮搜索次数，真实用量有数据才统计；不能把搜索费用假装已包含在 token 计费里。

验收：开/关请求差异；不支持模型禁用；服务器工具不落入本地未知函数错误；引用可打开；搜索超时后不丢已收到回答；纯聊天仍无法访问本地项目。

## 四、聊天记忆

原项目引用：[PersonaCLI/Herta](https://github.com/PersonaCLI/Herta)。本地仍保留 `packages/app-server/src/dream-trigger.ts`（空闲、冷却、材料量、忙碌与活动计数门槛）、`packages/knowledge/src/dream*` 和 `packages/memory`。但个人桌面在 `main/session-service.ts` 明确关闭 legacy dream；当前独立聊天不使用该通路。**不可直接把 enabled 改成 true**，否则重新启用旧模型/旁路配置并错误读取编程记录。

### C1：存储与召回

- 新增 ChatMemoryService，使用个人数据目录下独立版本化存储，与项目 `.herta/memory` 和代码任务隔离。复用原触发思路，不直接复用其旧客户端、全量 persona 训练或旧执行链。
- 每条记忆含稳定 ID、文本、类别、来源聊天/消息 ID、创建/更新时刻、revision、显式/自动来源；来源不明不能冒充用户陈述。保存采用串行原子写，迁移先备份。
- 首版记住用户明确的偏好、长期事项和明确“记住”内容，不把黑塔自述、角色扮演台词、猜测或网页文字自动当用户事实，不自动保存 Key/密码等凭据。
- 跨聊天按相关性和长度预算召回，注入为低优先级事实资料；近期用户更正优先。显示“本次参考的记忆”简洁入口。记忆不是上下文压缩，不删除原聊天、不伪报剩余上下文。
- 设置中的「黑塔的记忆」支持查看、搜索、直接修改/删除、开关自动整理；关掉后停止新后台任务。第一版建议默认开启自动整理，设置清楚注明会使用角色模型与少量 API 用量；本轮用户已提出此行为，实施时无需重复征求同一授权。

### C2：空闲整理

- 建议初值：用户无交互 5 分钟，且工作台/聊天均无运行轮、待审批、待补充回答；存在至少 2 个新增完成轮，距上次成功整理至少 30 分钟。定时器只在应用运行时工作，不安装系统计划任务。手动“整理现在的记忆”可跳过材料阈值。
- 使用**角色绑定模型**的当前已验证配置，经同一 provider 租约路径；没有可用角色绑定就暂停并提示，不擅自选其他模型或读取旧 DeepSeek 环境配置。
- 仅增量读取已完成的聊天片段，控制输入与输出预算；每次最多一个请求，不自行重试循环。失败退避，保留游标；退出重启不重复提交已完成片段。
- 前台新任务优先：中止后台请求；未提交提案不得落盘。提交前比较记忆 revision、源消息版本/删除状态和用户活动计数，避免后台旧结果覆盖用户更正。
- 模型只能返回候选记忆操作的受限结构；后台不能执行命令、搜索、读项目或安装插件。通过 schema、来源与容量检查后提交。
- 单独记账“记忆整理”的状态、用时及真实 token 用量；用户可关闭或手动整理，不混入普通对话统计。

### C3：对话式记忆管理

支持“记住我喜欢… / 把…改为… / 忘记… / 你记得哪些…”。经受限记忆指令通道调用增改查删 API；不为此给纯聊天开放通用工具。支持文本模型的结构化响应分支，验证输出，不用单一关键词正则误删引用内容。

对象唯一时直接执行并给小型结果回执；多条同名或指代不明时用既有问题卡让用户选择。只有保存成功才说“记住了”。删除/更正生成抑制记录与来源游标，阻止空闲重读旧历史把其恢复；用户之后显式要求重新记住可解除对应抑制。删除记忆不等于删除聊天原文，删除聊天也不得留下可继续提取的后台快照。跨此两类操作的行为要在设置说明且测试。

验收重点：显式保存后重启可召回；更正后旧提案不能覆盖；删除后空闲整理不复活；并发新聊天会让后台让路；取消不提交；纯聊天权限边界不扩大；无新材料不发请求。使用合成偏好测试，真实服务仅一个最小闭环。

## 五、工作台收敛与视觉

### D1：移除工作台回收区

移除常驻侧栏回收区，旧回收记录不自动永久清除、项目磁盘目录不删除。将已有恢复能力放在设置内低频历史管理入口，以便旧数据可找回；项目/任务管理保持原本的软移除语义，名称统一。独立聊天回收区不在本次用户要求范围，不顺便更改。

### D2：文本审计与等待文案

清理旧版本说明、开发术语、未实现入口、重复的“不会自动…”说明；必要边界集中到帮助/详细诊断，常规页面只显示当前有效状态。成功、失败、审批、危险操作和数据删除仍用明确事实表达。

等待文案使用角色气质，示例：请求已发出“消息正在跨越银河”；等待较久“像是遇到了伽马射线暴，稍等片刻”。旁边仍显示真实用时与停止按钮。这是氛围比喻，不能声称检测到了辐射、网络故障或真实进度。没有公开思考事件时不写“正在思考”；流式正文出现后退出等待文案，不持续抢占阅读。审批和补充问题不能被这类台词遮住。结束状态按用户要求保持普通准确表达。

将文案集中到状态映射，避免多个组件各用计时器；少量固定阶段，不频繁轮播。为未来动效预留状态类、统一时长变量、reduced-motion 分支；本轮不做角色动画或粒子效果。

### D3：浅色模式与整体观感

保留深紫默认，新增浅色及跟随系统，设置立即生效并持久化，启动无错误主题闪烁。以白/灰白为主、少量克制的紫色强调；暗色减少灰紫泥感。先梳理 reference-ux / atelier-baseline / round-two / round-three / round-ten / herta-chat 样式覆盖，建立语义颜色变量，不用颜色反转或再堆一层零散补丁。

覆盖标题栏、侧栏、消息、输入框、菜单、设置、审批/问题卡、diff、代码高亮、记忆/搜索状态、滚动条与选择色。新增行绿/删除行红在两种主题都保留符号与可读文字。角色插画不遮挡阅读；不新增大图生成需求。统一间距、边框、圆角、控件高度和图标尺寸。

验收用少量代表页与 100% / 125% / 150% 实际桌面缩放检查；尺寸模拟与 OS 缩放分开记录。键盘焦点、对比度和窄窗换行均可见，无单字竖排、菜单越界、浮层与输入框遮挡。

## 六、插件：后续可选设计，不阻塞主线

本轮先写接口 ADR，盘点现有工具 registry、IPC、Provider adapter 和 UI 命令入口。首版优先做“本地技能说明 + 经主进程代理的工具扩展”，不立即开放任意 renderer 注入、主进程 require 或应用源码自修改。

建议契约：manifest（ID/版本/API 版本/入口/能力）、启用/停用/升级、命名空间工具 schema、取消/超时/结果大小限制、配置与日志隔离。工具经原审批、工作区限制与审计通道；插件不能获得全量 Provider Key。若运行第三方代码使用独立进程，但不得把进程隔离宣传成完整 OS 沙箱。

理想工作流：用户让黑塔在项目中生成插件 → 隔离检查 → 应用展示将启用的具体能力 → 用户启用 → 可停用/回退。插件数据与应用安装文件分离，失败不会让主应用无法启动。不实现下载即执行或模型自授予能力；插件市场、任意远程安装和热替换应用核心留后续。

- 打包前更新进度、报告和已知边界；备份个人数据，检查迁移与原文件完整性，再安装。候选/安装版本与载荷一致；不擅自提交上传。
- 每阶段完成要区分“实现”“自动测试”“真实服务验证”“用户验收”，不以一个百分比掩盖未测试供应商。全部必需项完成后停止扩展，等待用户反馈。

## 八、下一次从哪里开始

1. 获取截图对应失败轮的已存诊断（只读、最小输出），核对 Provider/协议/revision 与失败工具。
2. 给工具参数错误细分码与回归用例，修复定位到的适配/截断问题及误导提示；同步核对文件快照。
3. 将 Provider 添加与验证做成一条流程，检查所有实际激活入口。
4. 再进入联网适配、聊天记忆、UI/主题；插件仅落 ADR，除非主线稳定且仍值得实施。
