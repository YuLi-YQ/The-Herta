# 插件文件与工作区修改提案

执行插件可以保存独立文本产物，也可以在工作台提出修改方案。产物保存、项目提案和真正应用是不同操作；安装权限不会跳过当前会话、项目基线及用户确认。

## 在界面中使用

打开当前会话的 **快捷操作 → 插件文件**，或从插件运行结果进入文件列表。

- **生成文件**：选择“查看”阅读内容；“保存副本”打开系统保存对话框，由你选择位置。原产物继续留在会话中。
- **修改提案**：先查看原文、修改后内容和实际差分，再点“申请应用”。只有真正写入完成才显示“已应用”。
- 应用期间可以取消；文件已变化或状态需要核对时，重新读取当前文件并生成新提案，不强行覆盖旧基线。

普通新建和修改在“工作区编辑”及“完全访问”档位由现有权限策略覆盖：明确点击“申请应用”后可以直接执行，不会为了重复确认再弹一次审批卡。“只读”和计划模式不允许应用。安装时勾选能力、插件自己展示的成功文字或生成提案，都不能替代这一步用户操作和执行时的权限检查。

聊天只能生成独立文件，不能提出或应用工作区修改。生成的文件在来源插件停用、更新或重启后仍可查看和另存；提案也可以继续检查，但应用时要求来源插件仍启用、内容哈希及授权修订与提案一致，否则需要重新运行插件生成提案。

## `artifacts.create`：保存文本产物

动作需声明并获得 `artifacts.create`。调用后保存到当前会话的插件文件库，不接受项目目录或任意磁盘路径：

```js
const file = await api.artifacts.create({
  name: 'notes.md',
  mime: 'text/markdown',
  text: '# 检查记录\n\n这是待用户查看的文字。\n'
});
return { artifactId: file.artifactId, saved: file.saved };
```

返回 `{ artifactId, name, mime, bytes, sha256, saved: true }`，bytes 与 sha256 按实际保存的 UTF-8 字节计算。内容不自动补换行或改写字符；空文本允许。不接受二进制、图片、PDF/DOCX 或任意 MIME，当前仅支持：

| MIME | 内容 |
| --- | --- |
| `text/plain` | 普通文本 |
| `text/markdown` | Markdown 文本 |
| `text/csv` | CSV 文本 |
| `application/json` | JSON 文本；插件负责生成正确语法，文件类型标签不是内容校验器 |

name 是单个文件名，最多 160 个 UTF-16 单位，无目录、盘符、ADS、Windows 保留名或尾点。text 最多 48,000 单位，实际 UTF-8 最多 128 KiB；整个能力参数仍受 64 KiB JSON 预算约束，因此这些单项上限不能同时用满。非法控制字符和不成对的 surrogate 拒绝。

保存副本由宿主读取已存内容，再打开保存对话框；对话框返回后重新核对会话归属与目标。新目标采用不可覆盖的发布方式；已有目标再次检查身份与原字节哈希后原子替换。保护目录和链接等检查仍生效。取消选择不删除产物；目标变化或保存失败不报告成已保存。

## `workspace.proposePatch`：冻结提案，再由用户应用

仅工作台动作可声明此能力，且创建时同样受当前权限和计划锁约束。参数为 `{ path, baseHash, content }`，content 是修改后的**完整文本**，不是补丁指令。普通现有文件先读取原字节哈希：

```js
const original = await api.workspace.readText({
  path: input.path,
  maxBytes: 131072
});
const proposal = await api.workspace.proposePatch({
  path: input.path,
  baseHash: original.sha256,
  content: input.content
});
return { proposalId: proposal.proposalId, status: proposal.status };
```

新建文件用 `baseHash: null`，要求目标尚不存在；不能用 null 覆盖现有文件。现有文件的 baseHash 为64位小写 SHA-256，必须与宿主实际读取的原字节一致。`readText` 在原有 `{ text, bytes }` 上兼容增加 `sha256`：text 可去除 UTF-8 BOM，bytes/sha256 仍包含 BOM。修改已有带 BOM 文件时，宿主保留 BOM，nextHash 依实际将写入的字节计算。

path 是项目内相对路径，最多 1,024 单位；实际文件系统也必须支持该路径。拒绝越界、绝对路径、ADS、危险保留名、受保护目录及链接跳转，不因为“完全访问”就扩大到任意文件。原文件仅接受有效 UTF-8 文本，最多 128 KiB；content 最多 48,000 单位，仍受64 KiB请求参数总预算约束。

成功返回 `{ proposalId, path, baseHash, nextHash, additions, deletions, status: 'pending' }`。宿主保存冻结的原文、修改后内容、差分、实际哈希、来源插件及工作区根身份。创建提案不写项目，也不会把插件操作伪装成上一轮模型的工具记录。

## 应用和异常状态

用户在独立文件面板明确申请后，宿主后台任务通过真实 Session 的工作区操作门运行；该操作不占用或伪造模型轮次，但与发送新业务、切换/重置工作区及另一写入互斥。当前会话、插件内容与授权、权限档位、计划锁、物理项目根和原文件哈希，在应用前及提交前重新核对。

| 状态 | 含义与下一步 |
| --- | --- |
| `pending` | 只保存提案，项目未因这份提案写入；可检查后申请应用 |
| `applying` | 当前宿主任务正在处理；可以请求取消，不能重复申请 |
| `applied` | 实际写入已经发生；保留时间、哈希及修改快照，不重复应用 |
| `denied` / `cancelled` / `failed` | 已知尚未提交的拒绝、取消或失败；可在检查后明确重新申请 |
| `conflict` | 基线或项目已变化；重新读取并生成新提案 |
| `needs-review` | 最终结果无法确定；先核对文件，不直接重试旧提案 |

实际写入前先持久记录 `applying`，其中保留原文（含 BOM）和预期前后哈希。新建采用不覆盖已有目标的发布；已有文件在最终同步复核后原子替换，不先搬走原文件再尝试恢复。提交前失败或取消保留原文件；提交后到来的取消不能让已发生的写入变成“未执行”。

若文件已写入而完成记录保存失败，当前进程保留真实“已应用”凭据并说明记录问题。重启读到未终结的 `applying` 只显示 `needs-review`，不会猜测成功或自动重放。宿主任务异常且不能确认终态时，尝试持久标记 `needs-review`；读取或保存仍失败则保留损坏原件，以有界的不确定记录阻止当前进程直接重试，后续读取/应用前再次尝试归档。已有真实提交凭据不会被降级成可重试失败。

提案文件和生成文件是独立记录，不是撤销功能。不要删除记录后假定项目恢复了原状；也不要把旧快照无条件写回，覆盖用户后来修改的内容。

## 配额和已知边界

| 存储 | 单聊天/任务 | 各自全局 | 单条 |
| --- | --- | --- | --- |
| 插件生成文件 | 最多100项、10 MiB | 100 MiB、最多5,000文件项 | 内容128 KiB，JSON封装512 KiB |
| 工作区修改提案 | 最多50项、16 MiB | 100 MiB、最多5,000文件项 | 原文128 KiB，含原文/新文/差分的记录1 MiB |

记录正文、损坏记录、孤儿和临时文件均占空间，不为腾额度静默删除原件。表中两套100 MiB限制是各库子额度；五类插件资料另共用512 MiB逻辑字节预算，私有资料每插件256 KiB。恢复与引用感知清理见[存储维护](PLUGIN_STORAGE_MAINTENANCE.md)。产物和提案不是缓存，不提供以删除记录代替撤销项目改动的入口。

存储按单宿主写入设计，不支持多个应用进程同时写同一profile。最后检查与文件替换不是操作系统级“哈希比较并交换”：其他进程在极窄窗口中修改文件或替换父目录，仍可能形成竞争。文件fsync加rename也不是目录项的断电事务，不承诺系统断电后所有记录与项目文件同时恢复。

临时文件只在归属仍匹配时清理；已经发布后，清理失败不把成功改报失败。持续无法删除临时硬链接时会保留残留，后续校验可能报告损坏，不能偷偷放宽读取规则。可确认的安装资料清理和私有资料恢复有独立入口，不会自动处理这些产物或提案。
